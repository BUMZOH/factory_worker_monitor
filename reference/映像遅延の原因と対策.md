映像遅延の原因と対策
OpenCV + RTSP + YOLO における「古いフレーム蓄積」問題
1. はじめに
工場の作業者監視アプリでは、ネットワークカメラの映像を OpenCV で受信し、
Ultralytics YOLO で人物検出を行っている。
今回、ネットワークカメラの映像に対して次の問題が発生した。
> **カメラの実際の時刻に対して、Python アプリに表示される映像が
> 十数秒遅れる。**
調査の結果、主原因は単純なYOLOの重さではなく、
カメラからのフレーム取得と重い画像処理を同じループで直列に実行していたこと
にあった。
結論は次のとおりである。
> **映像の取得速度より画像処理側が遅い場合、古いフレームを順番に処理すると
> 「現在」ではなく「過去」の映像を処理し続けることになる。**
対策として、カメラ読み込み専用スレッド `CameraReader` を作り、
> **常にカメラからフレームを読み続け、最新フレームだけを保持する**
方式に変更した。
その結果、十数秒あった遅延をほぼ解消できた。
---
2. システム構成
基本構成は次のとおり。
``` text
ネットワークカメラ
        ↓
       RTSP
        ↓
OpenCV VideoCapture
        ↓
      YOLO
        ↓
BBox・グリッド等を描画
        ↓
画面表示 / CSV保存 / MP4保存
```
RTSPはTCPを使用する。
``` python
os.environ[
    "OPENCV_FFMPEG_CAPTURE_OPTIONS"
] = "rtsp_transport;tcp"

camera = cv2.VideoCapture(
    rtsp_url,
    cv2.CAP_FFMPEG,
)
```
人物検出はYOLOで行う。
``` python
result = model.predict(
    source=frame,
    classes=[0],
    conf=CONFIDENCE,
    iou=IOU_THRESHOLD,
    imgsz=IMAGE_SIZE,
    verbose=False,
)[0]
```
現在の実運用候補は `IMAGE_SIZE = 1280` である。
---
3. 発生した現象と切り分け結果
実験で観測した遅延の目安は次のとおり。
条件                                 観測された遅延の目安
---
YOLO `imgsz=1280` + `sleep(0.1)`                   約25秒
YOLO `imgsz=1280` + sleepなし                      約19秒
YOLO `imgsz=640` + sleepなし                       約13秒
YOLOを外したRTSP確認                       約11～14秒程度
VLCで同じRTSPを確認                             約2秒程度
`CameraReader` 導入後                          ほぼ0～1秒
これらは厳密なベンチマークではなく、実機での切り分け時の観測値である。
特に重要だったのは、同じカメラ・同じRTSPをVLCで表示すると
十数秒の遅延が発生しなかったことである。
この結果から、カメラやネットワークだけではなく、
OpenCVアプリ側のフレーム取得方法を疑う必要があると分かった。
---
4. 切り分け① YOLOの画像サイズ
まずYOLOの処理負荷を疑い、
``` python
IMAGE_SIZE = 1280
```
から、
``` python
IMAGE_SIZE = 640
```
へ変更した。
遅延は小さくなったが、完全には解消しなかった。
さらに工場の実映像では、640では誤検出が発生することがあり、
1280では大幅に改善した。
したがって、単純に画像サイズを小さくして解決する方法は採用しなかった。
---
5. 切り分け② YOLOを外す
次にYOLOを外し、
``` text
RTSP
 ↓
OpenCV
 ↓
imshow()
```
だけで確認した。
それでも遅延が残った。
この時点で、
> **YOLOだけが遅延の原因ではない**
ことが分かった。
---
6. 切り分け③ VLCとの比較
同じRTSPをVLCで確認すると、
映像は滑らか
大きな時刻ジャンプがない
カメラ時刻とPC時刻との差は約2秒程度
だった。
一方、OpenCVの簡易表示では、カメラ映像内の時刻が
突然数秒進むような現象も観測された。
``` text
同じカメラ
同じネットワーク
同じRTSP

VLC     → ほぼリアルタイム
OpenCV  → 十数秒遅れる
```
この比較が、アプリ側のフレーム取得・処理方法に注目する
大きなきっかけになった。
---
7. 本質：フレームの生産速度と消費速度
ここが今回の最重要ポイントである。
カメラは継続的にフレームを送ってくる。
``` text
Frame 1
Frame 2
Frame 3
Frame 4
Frame 5
...
```
従来のMainループは概念的に次の構造だった。
``` python
while True:
    success, frame = camera.read()

    result = model.predict(frame)

    # 描画
    # 保存
    # 表示

    time.sleep(0.2)
```
つまり、
``` text
1フレーム読む
    ↓
YOLO
    ↓
描画
    ↓
保存
    ↓
表示
    ↓
sleep
    ↓
次のフレームを読む
```
である。
カメラからフレームが到着する速度より、
Main側の処理速度が遅ければ、処理側は過去のフレームを追いかけることになる。
---
8. 「処理が遅い」と「映像が遅れる」は別問題
例えばYOLOが1秒に2回しか処理できなくても、
``` text
現在時刻        12:00:10
処理中の画像    12:00:10
```
なら、表示更新は低速でも映像自体は現在に近い。
しかし、
``` text
現在時刻        12:00:30
処理中の画像    12:00:15
```
なら、15秒前の映像を処理している。
監視用途では後者の方が重大である。
したがって、
> **FPSが低いことと、映像が遅れていることは分けて考える。**
これは今回得られた非常に重要な知見である。
---
9. 古いフレームを追いかけるイメージ
カメラ側：
``` text
F1 F2 F3 F4 F5 F6 F7 F8 F9 F10 ...
```
処理側が十分速ければ、
``` text
F1 → 処理
F2 → 処理
F3 → 処理
```
と追従できる。
しかし処理側が遅いと、
``` text
Camera:
F1 F2 F3 F4 F5 F6 F7 F8 F9 F10

Main:
F1 --------処理--------
   F2 --------処理--------
      F3 --------処理--------
```
のような状態になる。
概念的には、
``` text
現在のカメラ映像
        ↓
      F100

Pythonが処理中
        ↓
       F70
```
となり、現在との差が大きくなる。
今回の十数秒の遅延は、この考え方で説明できる。
---
10. sleepをなくしても完全には直らなかった理由
`time.sleep()` 中はMainが次のフレームを読まないため、
sleepをなくすと遅延は改善した。
しかし完全には解消しなかった。
理由は、
``` text
camera.read()
YOLO
描画
保存
imshow
```
そのものにも時間が必要だからである。
つまりsleepは悪化要因にはなり得るが、本質は、
> **カメラ読み込みと重い画像処理を同じ直列ループに置いていたこと**
だった。
---
11. 対策：CameraReaderを別スレッドにする
対策として、カメラ読み込み専用スレッドを作った。
``` text
             ┌──────────────────┐
Camera ───→ │ CameraReader     │
             │ camera.read()    │
             │ camera.read()    │
             │ camera.read()    │
             │       ↓          │
             │ 最新frameを保持  │
             └────────┬─────────┘
                      │
                      ↓
             ┌──────────────────┐
             │ Main             │
             │ YOLO             │
             │ 描画             │
             │ CSV / MP4        │
             │ imshow           │
             └──────────────────┘
```
これにより、
``` text
カメラを読む処理
```
と、
``` text
YOLOなどの重い処理
```
を分離した。
---
12. CameraReaderの基本構造
基本形は次のようになる。
``` python
class CameraReader:
    """Continuously read frames from the camera."""

    def __init__(self, camera):
        self.camera = camera
        self.frame = None
        self.lock = threading.Lock()
        self.stop_event = threading.Event()
        self.thread = None

    def start(self):
        self.thread = threading.Thread(
            target=self._update,
            daemon=True,
        )
        self.thread.start()

    def _update(self):
        while not self.stop_event.is_set():
            success, frame = self.camera.read()

            if not success:
                continue

            with self.lock:
                self.frame = frame

    def read(self):
        with self.lock:
            if self.frame is None:
                return None

            return self.frame.copy()

    def stop(self):
        self.stop_event.set()

        if self.thread is not None:
            self.thread.join(timeout=5.0)
```
実際の最新版では、読み込み失敗時の再接続処理も追加している。
---
13. 最重要：最新フレームだけを保持する
核心はこの処理である。
``` python
self.frame = frame
```
フレームをQueueへ順番に蓄積するのではない。
``` text
self.frame = F1
self.frame = F2
self.frame = F3
self.frame = F4
```
のように、1個の変数を常に上書きする。
Mainが処理中に、
``` text
F2
F3
F4
F5
F6
```
が到着した場合も、
``` text
F2 → 上書きされる
F3 → 上書きされる
F4 → 上書きされる
F5 → 上書きされる
F6 → 最新として残る
```
となる。
つまり、
> **古いフレームを全部処理することを意図的に諦める。**
これがリアルタイム監視では重要である。
---
14. Mainは「次」ではなく「最新」をもらう
Mainでは、
``` python
frame = camera_reader.read()
```
とする。
これは考え方として、
> 「次のフレームをください」
ではなく、
> **「今持っている一番新しいフレームをください」**
である。
この違いが今回の遅延対策の本質である。
---
15. 従来方式と新方式
従来
``` text
Main
 ↓
camera.read()
 ↓
YOLO
 ↓
sleep
 ↓
camera.read()
 ↓
YOLO
```
MainがYOLOやsleepをしている間、Main自身はカメラを読まない。
CameraReader方式
``` text
CameraReader:
read → read → read → read → read → ...

Main:
最新frame取得
    ↓
   YOLO
    ↓
  sleep
    ↓
最新frame取得
```
Mainが重い処理をしている間も、CameraReaderは読み続ける。
---
16. CameraReader導入後にsleepを使える理由
現在はMainループ末尾に、
``` python
time.sleep(0.2)
```
を入れている。
従来方式では、
``` text
sleep
 ↓
カメラを読まない
 ↓
遅延増加
```
になりやすかった。
新方式では、
``` text
Mainがsleep
      ↓
CameraReaderは読み続ける
      ↓
古いframeを上書き
      ↓
Mainが起きる
      ↓
最新frameを取得
```
となる。
そのため、
> **CPU負荷を下げながら、フレームの鮮度を保てる。**
---
17. YOLOそのものが高速化したわけではない
CameraReaderは `model.predict()` を高速化する技術ではない。
今回 `IMAGE_SIZE = 1280` では、初回ウォームアップを除くと
推論時間はおおむね `0.15～0.23秒` を中心に推移し、 時々 `0.30秒前後`
になることもあった。
CameraReaderが改善したのは、
``` text
YOLOの計算速度
```
ではなく、
``` text
YOLOへ渡す画像の新しさ
```
である。
---
18. 工場監視に向いている理由
今回の目的は、作業者の現在の状態・位置を監視することである。
この用途では、
``` text
全フレームを必ず処理
```
することより、
``` text
現在に近いフレームを処理
```
することの方が重要である。
例えばF100～F104が到着済みで、1枚しか処理できないなら、
F100よりF104を処理した方が監視用途には適している。
つまり今回の設計は、
> **フレーム完全処理型ではなく、最新状態監視型**
である。
---
19. この方式が向かない用途
古いフレームを意図的に捨てるため、
高速現象を1フレームも逃したくない
製品通過を全数カウントする
瞬間的な異常を必ず解析する
動画の全フレームを後処理する
といった用途では、そのままでは適さない。
その場合はQueue、動画への先行保存、別プロセス、
GPU利用など別の設計が必要になる。
---
20. Lockを使う理由
CameraReaderは、
``` python
self.frame = frame
```
と書き込み、Mainは、
``` python
self.frame.copy()
```
と読み込む。
同じ変数へ別スレッドからアクセスするため、
``` python
with self.lock:
```
で保護する。
``` python
with self.lock:
    self.frame = frame
```
``` python
with self.lock:
    return self.frame.copy()
```
これにより、読み書きのタイミングが重なることを防ぐ。
---
21. `frame.copy()` の意味
MainではBBox、中心点、グリッド、時刻などを画像へ描画する。
もしCameraReaderの `self.frame` そのものをMainへ渡すと、
Readerが保持する画像とMainが加工する画像を共有してしまう。
そこで、
``` python
return self.frame.copy()
```
としてMain専用のコピーを返す。
``` text
CameraReader
    ↓
生の最新画像

Main
    ↓
コピーした画像
    ↓
BBox等を描画
```
という分離になる。
---
22. CPU負荷との関係
実験では概ね、
``` text
IMAGE_SIZE = 640

sleep(0.0) → CPU 約95%
sleep(0.1) → CPU 約90%
sleep(0.2) → CPU 約80%
sleep(0.3) → CPU 約70%
```
という傾向だった。
`IMAGE_SIZE = 1280` でもsleepを入れることでCPU負荷を抑えられた。
CameraReader導入後はsleepを、
> **映像遅延を生む待ち時間**
ではなく、
> **Main側のYOLO実行頻度を調整する手段**
として使いやすくなった。
---
23. `IMAGE_SIZE = 1280` を選んだ理由
640では工場映像で誤検出が見られたが、 1280では大幅に改善した。
1536も試したが、推論時間は概ね、
``` text
1280 → 約0.15～0.23秒中心
1536 → 約0.23～0.32秒中心
```
となり、1536は明確に重かった。
現段階では、
``` python
IMAGE_SIZE = 1280
time.sleep(0.2)
```
を、
``` text
検出精度
CPU負荷
更新頻度
リアルタイム性
```
のバランスが良い実運用候補としている。
---
24. CSVが完全な1秒間隔にならない理由
現在の保存判定は、
``` python
now = time.monotonic()

if now - last_record_time >= 1.0:
    ...
    last_record_time = now
```
である。
これは正確な毎秒タイマーではなく、
> **前回保存から1秒以上経過した最初のMainループで保存する**
方式である。
そのため、
``` text
12:00:01
12:00:02
12:00:03
12:00:05
```
のように秒が飛ぶ場合がある。
これはCameraReaderの不具合ではない。
将来、厳密な1Hz保存が必要になれば、保存周期もMainのYOLO処理から
分離することを検討する。
---
25. 通信断への対応
最新版ではCameraReaderの読み込み失敗時に、
``` python
if not success:
    print("Camera read failed.")
    logger.warning("Camera read failed.")

    with self.lock:
        self.frame = None

    self.camera.release()
    time.sleep(CAMERA_RETRY_INTERVAL)
    self.camera = reconnect_camera()

    continue
```
としている。
`self.frame = None` が重要である。
これをしないと通信断後も最後の古い画像をMainが繰り返し処理する
可能性がある。
Mainでは、
``` python
frame = camera_reader.read()

if frame is None:
    time.sleep(0.01)
    continue
```
となるため、復旧までYOLO処理を行わない。
---
26. 今後残っている課題
現在の `reconnect_camera()` は接続成功まで `while True` で再試行する。
そのため、
> **通信断中でもアプリを正常終了できる仕組み**
は次回の改造項目として残している。
今後はCameraReaderの `stop_event` を再接続処理にも渡し、
``` python
while not stop_event.is_set():
```
とする。
さらに、
``` python
time.sleep(CAMERA_RETRY_INTERVAL)
```
ではなく、
``` python
stop_event.wait(CAMERA_RETRY_INTERVAL)
```
を使えば、待機中でも終了要求へすぐ反応できる。
Main側も、`frame is None`
の状態でESC終了を扱えるように整理する必要がある。
---
27. Producer / Consumerとして考える
今回の問題は一般的なProducer / Consumer （生産者 /
消費者）の問題として考えると分かりやすい。
``` text
Producer = Camera
Consumer = YOLO
```
もし、
``` text
Producer速度 > Consumer速度
```
なら、すべてのデータを保持すればどこかにたまる。
通常のデータ処理ならQueueが適切な場合もある。
しかしリアルタイム監視で、
``` text
Queue:
F1
F2
F3
F4
F5
```
と古い画像をためると、それ自体が遅延の原因になる。
そこで今回は、
``` text
Latest Frame:
F5
```
だけを保持した。
これは、
> **Queueではなく「最新値共有」**
という設計である。
---
28. PLCやセンサ監視にも応用できる
この考え方はカメラ専用ではない。
例えばPLCから高速にデータを取得し、 UI表示が遅い場合にも、
``` text
PLC
 ↓
高速データ取得スレッド
 ↓
最新値を共有
 ↓
UIは必要な周期で最新値だけ取得
```
という設計ができる。
つまり今回のCameraReaderは、
> **高速I/Oと重い処理・低速UIを分離する**
という汎用的な設計パターンでもある。

30. 今後のトラブルシューティング手順
同様の遅延が起きた場合は、次の順番で確認する。
カメラ映像そのものの時刻を確認する
VLCなど別クライアントで同じRTSPを確認する
YOLOなど重い処理を外してOpenCVだけで確認する
sleepを一時的に外して変化を見る
`time.perf_counter()` でYOLO推論時間を測る
カメラ読み込みと画像処理が同じループか確認する
最新フレームだけを保持するReaderを検討する
CPU負荷と映像遅延を別々に評価する
`imgsz` と検出精度を実映像で比較する
通信断・再接続・終了処理まで実機試験する
特に、
> **VLCではリアルタイムなのにOpenCVでは遅れる**
場合は、ネットワークだけを疑い続けず、
アプリ側のフレーム取得方法を確認する価値が高い。

31. 最重要ポイントまとめ
原因
``` text
カメラは継続的にフレームを送信
        ↓
Mainがcamera.read()
        ↓
YOLOなどの重い処理
        ↓
次のcamera.read()が遅れる
        ↓
古いフレームを順番に処理
        ↓
実時間から映像が遅れる
```
対策
``` text
CameraReader専用スレッド
        ↓
camera.read()を継続
        ↓
最新frameだけ保持
        ↓
古いframeは上書き
        ↓
Mainは必要なときに最新frameを取得
        ↓
YOLO
```
実機での結果
``` text
従来
十数秒の映像遅延

        ↓

CameraReader導入

        ↓

ほぼリアルタイム
```
本質
> **リアルタイム監視では、「全フレームを処理すること」より
> 「最新フレームを処理すること」が重要な場合がある。**
さらに、
> **重い処理そのものを高速化できなくても、
> データ取得と処理を分離することでリアルタイム性を改善できる。**
これが今回の映像遅延問題から得られた、
最も重要で汎用性の高い知見である。

という考え方は、ネットワークカメラだけでなく、
PLC通信、センサ監視、設備状態表示などにも応用できる。
